## EPIC-01: Project skeleton, config & observability

**Goal:** A buildable Rust binary with CLI entrypoint, layered config, logging and error handling, so every later epic has a home.

**In scope**
- `Cargo.toml` with pinned stack: `ratatui`, `crossterm`, `tokio`, `reqwest` (rustls), `rusqlite`, `serde`, `keyring`, `uuid`, `tracing`, `thiserror`/`anyhow`, `clap`.
- Module layout: `src/main.rs`, `src/cli/`, `src/config/`, `src/error.rs`, `src/log.rs`.
- CLI subcommand skeleton (`auth`, `logout`, `sync`, `add`, `today`, default = TUI) with stubs returning "not implemented".
- Config loading from `$XDG_CONFIG_HOME/todoist-tui/config.toml` (+ platform fallbacks): `sync_interval`, `theme`, `keymap`, `default_view`; defaults when file missing; typed errors on malformed TOML.
- `tracing` to a rotating file under the state dir; no stdout noise in TUI mode; log redaction helper for secrets.
- Repo hygiene: `rustfmt.toml`, `clippy` lint config, CI workflow running `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`.
- Fill the Project section of `CLAUDE.md` (name, stack, test/lint commands, layout conventions).

**Out of scope**
- Any network, DB or UI behaviour (stubs only).

**Dependencies:** none.

**Acceptance**
- `cargo build --release` succeeds on Linux and macOS; `cargo clippy -- -D warnings` clean.
- `todoist-tui --help` lists `auth`, `logout`, `sync`, `add`, `today`.
- With no config file present, defaults load and `sync_interval == 60`.
- Config at `$XDG_CONFIG_HOME/todoist-tui/config.toml` overriding `sync_interval = 120` and `default_view = "today"` is reflected in the loaded `Config` (unit test with temp dir).
- Malformed TOML returns a typed `ConfigError` with file path and line, not a panic.
- `tracing` writes to the state dir log file; a test asserts a string tagged as secret is rendered as `***` and never verbatim.
- CI workflow runs fmt + clippy + tests on push.

**Risks / open questions**
- `keyring` crate pulls platform deps (dbus/secret-service on Linux) — verify build on minimal containers early.
- Windows path/dir fallbacks are best-effort per NFR.

## EPIC-02: Auth & token storage

**Goal:** Owner can store a personal API token securely and clear it, and the app can obtain it for API calls.

**In scope**
- `todoist-tui auth` — prompt for token without echo, validate it with a cheap authenticated call, store it.
- OS keyring storage via `keyring`; fallback to `$XDG_CONFIG_HOME/todoist-tui/token` with 0600 perms when keyring is unavailable, with explicit user-visible notice.
- `todoist-tui logout` — wipes token from keyring/file **and** wipes the local cache DB (NFR).
- `TokenSource` abstraction (seam for later OAuth) + "not authenticated" error path used by all other commands.
- Guarantee token never reaches logs or error messages.

**Out of scope**
- OAuth, multi-account, token refresh.
- Cache schema itself (EPIC-04 owns it; logout calls a delete hook).

**Dependencies:** EPIC-01.

**Acceptance**
- `auth` with a valid token stores it; a subsequent process run retrieves the same token without prompting.
- `auth` with an invalid token exits non-zero with "invalid token" and stores nothing.
- Terminal echo is disabled during token entry (manual check documented) and the token never appears in argv.
- Keyring-unavailable path writes the fallback file with mode `0600`; test asserts permission bits on Unix.
- `logout` removes keyring entry + fallback file + cache DB file; running any command afterwards reports "not authenticated".
- Unit test: formatting an auth error or the `Config`/client debug output contains no token substring.

**Risks / open questions**
- Headless Linux (no secret-service) is common → fallback path must be well-tested, not an afterthought.

## EPIC-03: Todoist Sync API client

**Goal:** A typed, resilient async client for `POST /api/v1/sync` that other layers can call without knowing HTTP details.

**In scope**
- `reqwest` client (rustls, HTTPS only, timeouts, `Authorization: Bearer`).
- Request model: `sync_token`, `resource_types` (exactly `projects`, `items`, `sections`, `labels`, `notes`, `filters`, `user`, `day_orders`), `commands`.
- Response model: resource arrays, `sync_token`, `full_sync`, `temp_id_mapping`, `sync_status`, `full_sync_date_utc`; serde types tolerant of unknown fields.
- Domain structs for Project, Item, Section, Label, Note, Filter, User incl. `is_deleted`, `checked`, due/deadline, priority, labels, `parent_id`, `section_id`, `child_order`.
- Retry with exponential backoff + jitter on network error / 5xx; on 429 honour `retry_after`; bounded attempts, typed `ApiError` (auth / rate-limited / server / transport / decode).
- Wiremock-based integration tests for the above.

**Out of scope**
- Persistence, queueing, scheduling, conflict handling.
- Any endpoint other than `/sync` (quick-add and completed-tasks endpoints are gated on open questions 1 and 3).

**Dependencies:** EPIC-01, EPIC-02.

**Acceptance**
- Full-sync request body serialises `sync_token: "*"` and exactly the eight required `resource_types`; a test asserts no extra types are sent.
- A recorded/fixture full-sync response deserialises into domain structs with no field loss for the fields listed above.
- Mocked 500 → client retries with increasing delay and succeeds on the 3rd attempt; attempt count asserted.
- Mocked 429 with `Retry-After: 2` → client waits ≥2s before retry (asserted via injected clock, not real sleep).
- Mocked 401 → `ApiError::Unauthorized` returned immediately, no retry.
- Unknown JSON fields in a response do not cause a decode error.

**Risks / open questions**
- API v1 field shapes (esp. due/deadline objects, `day_orders`) must be verified against live responses; fixtures may drift.

## EPIC-04: SQLite cache & delta application

**Goal:** All synced resources plus `sync_token` persist locally so the TUI can start from cache with no network.

**In scope**
- `rusqlite` store: schema + migrations, tables for projects, items, sections, labels, notes, filters, user, day_orders, plus a `meta` table (`sync_token`, `last_sync_at`, `full_sync_date_utc`).
- DB file in the state dir with 0600 perms; `delete_all()` hook used by `logout`.
- Delta apply: upsert on present resources, remove on `is_deleted: true`, full-sync replace semantics; single transaction per sync response.
- Read queries needed by views: tasks by project/section/parent, today, upcoming, by label, inbox; ordered by `child_order`.
- Indices to keep queries fast at 5k+ items.

**Out of scope**
- Write queue (EPIC-05), scheduling (EPIC-06), UI.
- Encryption at rest (open question 5).

**Dependencies:** EPIC-03 (domain types).

**Acceptance**
- Fresh DB is created with mode `0600`; migration runs idempotently (run twice → same schema version, no error).
- Applying a full-sync fixture then an incremental fixture yields the expected final row set (unit test): updated item changed, `is_deleted: true` item gone, new item present.
- `sync_token` round-trips across process restart.
- Applying a malformed/partial delta rolls back the whole transaction; prior state intact.
- Seeded 5k items: "today" query and "project tasks" query each return in <50ms on dev hardware (benchmark test asserts a bound).
- `delete_all()` removes the DB file/contents; a following open creates a fresh empty DB.

**Risks / open questions**
- Sub-task and section ordering semantics (`child_order`, `day_orders`) need verification against real data.

## EPIC-05: Durable write queue & command execution

**Goal:** Local edits are recorded as Sync API commands that survive crashes, flush in batches, and never duplicate or lose a write.

**In scope**
- `commands` table in SQLite: client `uuid`, `type`, args JSON, `temp_id`, state (`pending|in_flight|failed`), attempts, created_at, error.
- Enqueue API used by all mutating actions; optimistic local apply to the cache in the same transaction as enqueue.
- Batch flush: group pending commands into one `/sync` request, preserving order.
- `temp_id_mapping` resolution: rewrite temp IDs to real IDs in cache rows **and** in still-pending queued commands that reference them (e.g. task created in a newly created project).
- Per-command `sync_status` handling: `ok` → drop from queue; error → mark failed with error text, keep it out of the retry loop, expose for UI; define per error class whether optimistic local state is kept or rolled back.
- Idempotency: a command re-sent after an ambiguous failure reuses the same `uuid`.

**Out of scope**
- Scheduling/when to flush (EPIC-06), UI surfacing (EPIC-07), conflict resolution policy (EPIC-06).

**Dependencies:** EPIC-04.

**Acceptance**
- Enqueue + optimistic apply are atomic: simulated crash (transaction abort) leaves neither a queued command nor a mutated row.
- Process killed with N pending commands → on restart the same N commands are present with identical `uuid`s and are flushed exactly once (mock API asserts each `uuid` seen once across both runs).
- Create project (temp_id A) + create task in project A in one batch → response `temp_id_mapping` rewrites both the cached rows and any remaining queued command referencing A; no temp id remains in the DB afterwards.
- Mixed `sync_status` response (one `ok`, one error) → ok command removed, failing command marked `failed` with its error message retrievable; queue does not stall.
- 100 pending commands flush in a single `/sync` request (or documented max batch size), order preserved.
- Unit tests cover delta apply + temp_id remap + queue (explicit NFR testing requirement).

**Risks / open questions**
- Per-error-type keep-vs-rollback matrix (FR-13) must be defined from real Sync API error codes; needs a short spike task.
- Recurring-task completion behaviour offline (open question 6).

## EPIC-06: Sync engine orchestration (background, offline, conflict policy)

**Goal:** A background task that keeps cache and server converged on schedule and on demand, works offline, and applies the stated conflict policy.

**In scope**
- Sync actor on `tokio`, owning the API client + store; communicates with the rest of the app over channels only (UI never blocks on network).
- First run → full sync (`sync_token=*`); afterwards incremental with stored token.
- Scheduled sync every `sync_interval` (default 60s) + on-demand trigger; de-dup overlapping runs.
- Flush pending queue then pull deltas in one cycle; conflict policy FR-18: server state wins, pending local commands replayed on top (LWW).
- Offline detection: transport errors → `Offline` state, stop hammering, resume automatically; all edits keep working against cache.
- Large `full_sync_date_utc` lag detection → follow a full sync with an immediate incremental sync.
- Emit `SyncState` events: `Synced{at}` / `Syncing` / `Offline` / `Pending(n)` / `Error{msg}`.

**Out of scope**
- Rendering the state (EPIC-07), command semantics (EPIC-05).

**Dependencies:** EPIC-05.

**Acceptance**
- First run with empty DB issues exactly one request with `sync_token: "*"`; second run uses the stored token.
- With a mock API, a local edit is flushed and visible in a subsequent pull within one cycle; end-to-end latency under mock <5s (matches goal "visible in Todoist ≤5s").
- Remote-only change appears in cache within one `sync_interval` (test uses a short interval) and immediately on manual trigger.
- Offline: API mock down → edits still apply to cache, state becomes `Offline`, no unbounded retry storm (max attempt rate asserted); when mock returns, queue flushes with zero duplicates and zero losses.
- Conflict case: same item edited remotely and locally-pending → after a cycle, server value is applied and the pending local command is replayed on top, final value = local (LWW), asserted in test.
- Overlapping triggers while a sync is in flight collapse into one request.
- `full_sync_date_utc` older than threshold → an incremental sync immediately follows the full sync (asserted request sequence).

**Risks / open questions**
- LWW only; field-level merge is open question 2.
- Interval default vs rate limits (open question 4).

## EPIC-07: TUI shell — layout, navigation, status bar, keymap

**Goal:** A usable read-only terminal UI over the cache: sidebar, task list, detail pane, status bar, vim keys, help overlay — starting in <500ms.

**In scope**
- `ratatui` + `crossterm` app loop, alternate screen, resize handling, clean restore on panic/exit.
- Sidebar: Inbox, Today, Upcoming, Projects tree (nested sub-projects, collapsible), Labels, Filters.
- Task list for the selected view, grouped by section where applicable, sub-tasks indented, priority/due/labels indicators.
- Detail pane: content, description, due, deadline, priority, labels, comments (read).
- Status bar: sync state (synced / syncing / offline / N pending / error) + last sync time, fed from EPIC-06 events.
- Keymap: vim-style `j/k`, `h/l`, `g/G`, `/`, `r` (manual sync), `q`; loaded/overridable from config; `?` help overlay listing all bindings.
- Theme handling for 256-color and truecolor; min 80x24 guard with a graceful "terminal too small" message.

**Out of scope**
- Any mutation (EPIC-08/09), search execution internals (EPIC-10 owns matching; `/` key just opens the prompt).

**Dependencies:** EPIC-04 (reads), EPIC-06 (sync state events).

**Acceptance**
- Cold start with a populated 5k-item cache renders the default view in <500ms with no network call (measured, logged, asserted in a timing test).
- Key input → render completes in <16ms p95 at 5k items (benchmark).
- Navigating with `j/k/h/l/g/G` moves selection as specified; snapshot tests of the rendered buffer for sidebar, list and detail.
- Status bar shows each of the five states driven by injected `SyncState` events; last sync time updates after a sync.
- `?` overlay lists every bound key, and a test asserts the overlay content is generated from the keymap (no drift).
- A custom keymap in `config.toml` rebinds a key and the help overlay reflects it.
- Terminal resized below 80x24 shows the guard message and recovers when enlarged; quitting always restores the terminal (including on panic).

**Risks / open questions**
- Wireframe authority (open question 8).

## EPIC-08: Task actions (write path in UI)

**Goal:** Owner can create, edit, complete, delete, move, reorder tasks and add comments from the TUI, applied optimistically and queued for sync.

**In scope**
- Add task form: content, description, project, section, parent, due string, priority, labels.
- Inline/form edit of task fields.
- Complete / uncomplete.
- Delete with confirmation.
- Move between project / section / parent.
- Reorder within a list (`child_order` updates).
- Add and view task comments (text only).
- Every action → enqueue command (EPIC-05) + optimistic cache update + immediate UI reflection, including while offline.
- Per-command failure surfaced in the UI (status bar + an errors view/toast with the server message).

**Out of scope**
- Quick add / NL parsing via server endpoint only (DECIDED, D1 — lands as CLI task in EPIC-11; TUI binding post-EPIC-11).
- Completed-task browsing (open question 3), reminders, attachments, reactions.

**Dependencies:** EPIC-05, EPIC-07.

**Acceptance**
- Each of add / edit / complete / uncomplete / delete / move / reorder / comment produces exactly one correctly-typed Sync command with a fresh `uuid` (creates carry a `temp_id`) — asserted per action against the mock API.
- UI reflects every action immediately (before any network round-trip), verified with the API mock paused.
- Delete asks for confirmation; declining enqueues nothing and changes nothing.
- Offline: all of the above work; after reconnect every change lands server-side once, verified with zero duplicate `uuid`s.
- Creating a task in a just-created (still temp-id) project results in the task attached to the real project id after `temp_id_mapping` resolution.
- A command rejected by the server surfaces its error text in the UI and the local state follows the keep/rollback rule defined in EPIC-05.
- Reorder persists: after a sync cycle and app restart, order matches.

**Risks / open questions**
- Recurring-task completion offline (open question 6) — behaviour must be documented in the help/docs whichever way it is decided.

## EPIC-11: Non-interactive CLI

**Goal:** Scriptable commands that work without opening the TUI.

**In scope**
- `todoist-tui add "<text>"` — add a task to Inbox; online parses via server-side quick-add (D1), offline queues raw text ("added unparsed"), enqueue + flush, exit code reflects success.
- `todoist-tui sync` — force a full sync cycle and exit, printing a one-line summary.
- `todoist-tui today` — print today's tasks to stdout in a stable, scriptable plain-text format (and `--json`).
- Offline behaviour: `add` queues locally and reports "queued (offline)" with exit code 0; `sync` reports failure with non-zero exit.

**Dependencies:** EPIC-06 (sync cycle), EPIC-05 (queue).

**Acceptance**
- `add "buy milk"` with mock API online → task exists in cache and exactly one command sent; exit code 0.
- `add` while offline → command queued durably, exit 0 with "queued" message; a later `sync` flushes it exactly once.
- `sync` prints last sync time and pending count, exit 0 on success, non-zero when offline/unauthenticated.
- `today` output is deterministic for a fixed fixture cache (golden-file test) and contains no ANSI escapes when stdout is not a TTY.
- `today --json` emits valid JSON validated in test.
- All three commands run without entering alternate screen (no TUI artefacts in piped output).

**Risks / open questions**
- NL parsing relies on the server quick-add endpoint (D1); a separate offline parser is explicitly rejected.

## EPIC-12: Hardening, packaging & docs

**Goal:** Ship a trustworthy single binary with the required test coverage, perf proof, security checks and user documentation.

**In scope**
- Integration test suite against mocked Sync API (wiremock) covering the full offline→online cycle; CI runs it.
- Performance gates in CI: cold start <500ms, input→render <16ms, sync request <2s p95 (mocked), 5k-task dataset.
- Security checks: no token/PII in logs (automated log scan test), DB and token file perms, HTTPS-only enforced, `logout` wipes everything.
- Manual test plan against a real account using a dedicated test project (documented checklist in `docs/`), incl. the 80x24 / truecolor / Linux+macOS terminal matrix.
- Release: `cargo install` support, static-ish single binary, GitHub Release workflow for Linux + macOS artifacts; optional Homebrew/AUR recipe.
- Docs: README (install, auth, keybindings, config reference, offline/sync behaviour, troubleshooting), CHANGELOG.

**Dependencies:** EPIC-08, EPIC-09, EPIC-10, EPIC-11.

**Acceptance**
- CI pipeline is green running fmt, clippy, unit, integration (wiremock) and perf-gate jobs; a deliberate regression in any gate fails the build (verified once).
- Automated test greps the generated log file for the test token and asserts zero occurrences.
- Release workflow produces downloadable Linux and macOS binaries from a tag; `cargo install --path .` works on a clean machine.
- README documents every default keybinding and every config key, and a test/script asserts the documented keymap matches the code's default keymap.
- Manual test checklist exists in `docs/` and has been executed once against the dedicated test project, with results recorded.
- `logout` followed by a fresh start behaves like first run (full sync after re-auth) — verified manually and in integration test.

**Risks / open questions**
- Fully static binaries on macOS/Linux with `keyring` platform deps may not be achievable; may need per-platform builds.
- Perf gates in CI are noisy; may need generous thresholds plus local benchmarks as the real signal.
