# REQ-001: Todoist TUI (Rust) with two-way sync

- Owner: Pasha
- Client / product: Personal / todoist-tui
- Priority: P3
- Target date: <yyyy-mm-dd>

## Problem
Managing Todoist means leaving the terminal for the web/desktop app. Context switch, mouse-heavy, slow for keyboard-first workflow. No good Rust-native, offline-capable terminal client syncing with personal Todoist account.

## Goal
Keyboard-driven terminal client that reads/writes Todoist data and stays in sync with the account.

- Startup to usable UI < 500ms from local cache (no network wait).
- Any change made in TUI visible in Todoist web/mobile within ≤ 5s when online.
- Changes made elsewhere visible in TUI within ≤ 60s (background incremental sync) or instantly on manual sync.
- Zero lost or duplicated writes across offline → online transitions.

## Users / roles
- Owner (single user): authenticates with own Todoist account, views/creates/edits/completes tasks, projects, sections, labels from terminal.

## Functional requirements

### Auth & config
1. The system shall authenticate via Todoist personal API token (Bearer) from Todoist integration settings.
2. The system shall store the token in OS keyring (fallback: config file with 0600 perms), never in logs.
3. The system shall read config from `$XDG_CONFIG_HOME/todoist-tui/config.toml` (sync interval, theme, keymap, default view).
4. The system shall provide `todoist-tui auth` / `logout` commands to set/clear token.

### Sync engine
5. The system shall use Todoist API v1 `/api/v1/sync` endpoint.
6. The system shall do full sync (`sync_token=*`) on first run, then incremental sync using stored `sync_token`.
7. The system shall request only needed `resource_types`: `projects`, `items`, `sections`, `labels`, `notes`, `filters`, `user`, `day_orders` (others excluded).
8. The system shall persist all synced resources + `sync_token` in local SQLite cache.
9. The system shall apply incremental deltas (upsert; remove on `is_deleted: true`).
10. The system shall queue local writes as Sync API commands, each with client-generated `uuid` (idempotency) and `temp_id` for creates.
11. The system shall batch queued commands into one request where possible.
12. The system shall resolve `temp_id_mapping` from response and rewrite local IDs (including references, e.g. task in new project).
13. The system shall read per-command `sync_status`; on error, mark command failed, surface error in UI, keep/rollback local state per error type.
14. The system shall retry on network failure / 5xx with exponential backoff; on 429 respect `retry_after`.
15. The system shall work offline: all edits apply optimistically to local cache and flush when online.
16. The system shall run background sync on interval (default 60s) and on demand (`r` key).
17. The system shall detect large `full_sync_date_utc` lag and follow with incremental sync.
18. Conflict policy: server state wins after flush; pending local commands replayed on top (last-write-wins).

### Views & navigation
19. The system shall show sidebar: Inbox, Today, Upcoming, Projects (tree, with sub-projects), Labels, Filters.
20. The system shall show task list for selected view, grouped by section where applicable, with sub-tasks indented.
21. The system shall show task detail pane: content, description, due, deadline, priority, labels, comments.
22. The system shall show status bar: sync state (synced / syncing / offline / N pending / error), last sync time.
23. The system shall support vim-style keys (`j/k`, `h/l`, `g/G`, `/` search) and configurable keymap.
24. The system shall provide `?` help overlay with all keybindings.

### Task actions
25. Add task (content, description, project, section, parent, due string, priority, labels).
26. Edit task fields inline / via form.
27. Complete / uncomplete task.
28. Delete task (with confirm).
29. Move task between project / section / parent.
30. Reorder tasks within list.
31. Add / view task comments (text only).
32. Quick add with natural language (`tomorrow 5pm #Work @label p1`) — resolved, see Decision D1.

### Project / section / label actions
33. Add, rename, archive, delete project (confirm on delete).
34. Add, rename, reorder, delete section.
35. Add, rename, delete personal label.

### Search & filter
36. Local fuzzy search over cached tasks (content, description).
37. Show tasks of saved Todoist filters (read-only).

### CLI (non-interactive)
38. `todoist-tui add "<text>"` — add task to Inbox without opening TUI.
39. `todoist-tui sync` — force sync and exit.
40. `todoist-tui today` — print today's tasks to stdout (scriptable).

## Non-functional
- Performance: cold start from cache < 500ms; key input → render < 16ms; handle 5k+ tasks without lag; single sync request < 2s p95 on normal connection.
- Reliability: no lost/duplicate writes (command `uuid` idempotency + durable local queue in SQLite, survives crash/kill).
- Security / compliance: token in OS keyring; HTTPS only; no token/PII in logs; cache DB file perms 0600; `logout` wipes token + cache.
- Rate limits: respect Todoist request/command limits; batch commands; backoff on 429.
- Platforms: Linux, macOS (primary); Windows (best effort). Terminals: 256-color + truecolor; min 80x24.
- Tech stack: Rust (stable), `ratatui` + `crossterm` (UI), `tokio` + `reqwest` (async HTTP, rustls), `rusqlite` (cache), `serde` (JSON), `keyring`, `uuid`, `tracing` (logs to file).
- Architecture: UI thread never blocks on network; sync engine runs as background task, communicates via channels.
- Distribution: single static binary; `cargo install`, GitHub Releases (Linux/macOS), optional Homebrew/AUR.
- Testing: unit tests for delta apply + temp_id remap + queue; integration tests against mocked Sync API (wiremock); manual test against real account (dedicated test project).

## Out of scope
- OAuth flow / multi-user / multi-account (personal token only, v1).
- Team workspaces admin, sharing, collaborators, invitations.
- Reminders (create/edit), location reminders.
- File attachments upload, comment reactions.
- Creating/editing filters (view only).
- Calendar / board view modes.
- Notifications / live notifications.
- Webhooks (TUI is client-only, polling sync).
- Activity log, productivity stats, karma.

## Decisions

- **D1 — Quick add (FR-32), 2026-10-27:** Use the server-side quick-add endpoint (online only); no local NL parser. Offline, `add` queues the text verbatim as a plain `item_add` command and reports "added unparsed (offline)". Ships first in the non-interactive CLI (EPIC-11); TUI binding follows later. EPIC-03 gains the endpoint client.
- **D2 — Conflict policy (FR-18), 2026-10-27:** Last-write-wins confirmed as the v1 policy, as written in FR-18. Sync-command granularity already merges non-conflicting field edits (local `content` edit + remote `due` edit both survive); only same-field concurrent edits resolve LWW. No field-level merge in v1. EPIC-06 acceptance must include a cross-field test pinning this behaviour.
- **D3 — Completed tasks (FR-27), 2026-10-27:** Completed-history browsing deferred to post-1.0 (separate plan-limited endpoint not worth an epic in v1). v1 keeps `checked: true` items in the local cache (EPIC-04 retention) so `uncomplete` works on recently completed tasks (EPIC-08). A small verification task in EPIC-03/04 confirms how long `checked` items remain in the sync payload.

## Open questions (remaining)

- Recurring tasks: complete behaviour (advance due date) — rely fully on server response, or predict locally for offline?
